Board child cards (subtasks)

Design spec · 2026-09-03 · replaces the JSON checklist built earlier the same day · status: awaiting Shazwan's review

A T.A.A. card can hold child cards. On the board the parent looks like a stack. Opening the parent shows an overview of parent plus children in the space beside the drawer. Clicking a child switches the drawer to it. The parent cannot reach Done while a child is open.

Mockup only shows layout and hierarchy. Real spacing, type sizes and colours come from the existing .wc and .wd rules in resources/css/app.css.

2. What a child card is

A child is a normal work_items row with parent_id set. It reuses everything a card already has: title, description, priority, due date, labels, links, participants, comments, mentions. It differs in four ways.

FieldParent (as today)Child
statustodo / prog / review / donetodo or done only. "Open" in the UI. Never prog or review, so it never records a progress stint.
typetask / assignment / adhocCopied from the parent at creation, then ignored. The drawer hides the picker.
project_id, timesheet_category_idOwn valuesCopied from the parent at creation, drawer hides the pickers. Children never produce timesheet rows of their own, the parent's stint carries the hours. They do feed the parent row's note, see section 6.
employee_idBoard ownerSame as the parent's. The child lives on the parent's board and nowhere else.
parent_idnullThe parent's id. One level only: a child cannot have children.
sort_orderPosition in its columnPosition under the parent.
due_atSynced to Google CalendarNot synced. The parent's date is the one that matters to the calendar.
archived_atOwnFollows the parent: archiving, restoring or deleting the parent does the same to every child.
Decision: children are rows on the same table, not a new table, and not JSON. It is the only shape where "click a child, the drawer shows it" costs nothing: the drawer, comments, mentions, participants and the show endpoint already work on a WorkItem.

3. Rules

  • Add a child: anyone who can open the parent (BoardRules::authorizeAccess): owner, assigner, participant, a manager over the owner, or anyone canSeeAll admits within their scope.
  • Tick / untick a child: same grant as above. Ticking is moving the child between todo and done, so it is the existing move rule.
  • Edit or delete a child's fields: authorizeManage evaluated against the parent, so the person who can edit the parent can edit its children. A participant who added a child cannot rename it afterwards. Simple, one rule, and it matches how the checklist was gated.
  • Done gate: a parent cannot move to done while any child is todo. Enforced in BoardRules::assertChildrenDoneForStatus(), called by WorkItemController::move() and MoveCardTool. Message: "2 subtasks still open. Tick them off before moving this card to Done."
  • Parent moves elsewhere freely. Todo, In Progress, In Review carry no gate.
  • Depth one. store() refuses a parent_id that itself has a parent (422). Same in CreateCardTool.
  • Cross-tenant and cross-board: the parent must belong to the current tenant, and the child is always created on the parent's board (employee_id copied), never on the caller's.
  • Shared-card due date rule (assertDueDateRetained) applies to children as it does to parents. No exception.

4. Board (personal)

  • Children never render in a column. The column lists, counts, filters, sorts and the archived list all ignore them.
  • A parent with children gets wc--stack: two hairline layers peeking out below (pure CSS, ::before/::after) and the existing wc-sub counter (1/3, green when complete).
  • Dragging the parent drags the stack as one card, nothing new there.
  • Team board (team-board.blade.php, team-board.js): same stack look, same overview, but the overview is read only. No add, no tick, consistent with that board being view and comment only.
  • Dashboard "work" widget and BuildsNav counts: parents only.

5. Overview and drawer

  • Opening any card opens the drawer as today. When the card is a parent with children, or a child, the scrim to the left carries an overview panel (300px, centred vertically near the top): the parent card face, then the children as compact rows (tick, title, due or first participant initials), then + Add a subtask for anyone with access. A parent with no children shows nothing extra: no empty panel, the add button lives in the drawer under a new Subtasks heading so the first child can be created.
  • Clicking the parent face in the overview, or the back link, switches the drawer to the parent. Clicking a child row switches the drawer to that child. It is the same drawer, the same openCard() path, with drawer.parent set so the back link and the overview know what to show. The URL keeps tracking the card shown (pushState, already in place for deep links).
  • Ticking from the overview calls move with todo or done on the child, then repaints the parent's card face from the response. The child drawer shows an Open / Done toggle in place of the four column tabs.
  • Adding from the overview: an inline title input, Enter creates via store() with parent_id, the new row appears, the parent's face repaints.
  • Child drawer hides: type picker, category and project pickers, the archive action. Shows everything else.
  • Clicking the scrim outside both panels still closes the drawer.

6. Timesheet

Children never become rows on the capture grid. The parent's row is offered exactly as today (every day it sits in In Progress or In Review, and the day it goes straight to Done). What changes is the row's note, which starts empty today.

  • Prefill: when the parent's row is offered for a day, its note is prefilled with the child cards that are yours and were ticked done on that day (done_at on that date). One bullet per child, the child's title. A day with no such ticks keeps an empty note, same as now.
  • Yours means you are on the child's people list. A child with nobody on it counts as the parent owner's, so the owner sees the unassigned ones and a participant sees only the ones they were put on. Whoever the parent row is offered to (owner or participant of the parent, per BoardSuggestions::cardsFor()) gets their own view of the note.
  • Prefill only, never overwrite. The note is filled on the suggested row before the staffer saves it. A row already saved keeps whatever note it has; a child ticked later that day does not rewrite it. The staffer can edit or clear the prefilled note like any other.
  • Untick after save: nothing happens to the saved note. The note is a record of what the person wrote down, not a live view.
  • Format: the note field holds sanitised HTML (the row editor is Quill), so the prefill is a <ul> of <li> titles, escaped. It renders through the existing .uj-markdown block on the grid.
  • Code: BoardSuggestions::forWeek() gains one query: children of the offered cards, with participants, done between week start and end, grouped by parent and done date. The description in the row array is built from it. No change to WeekWriter, the MCP timesheet tool, or the grid markup.

7. Data and code changes

Migration

work_items
  + parent_id  unsignedBigInteger nullable, index, FK work_items.id ON DELETE CASCADE
  - subtasks   (drop the JSON column from the checklist build; nothing has shipped on it)

Model

  • WorkItem::parent(), WorkItem::children() (ordered by sort_order), isChild(), openChildCount(), childSummary().
  • Global scope ParentOnly: whereNull('parent_id') on every query by default. This is what keeps the twenty existing query sites (board data, dashboard, nav counts, timesheet suggestions, workforce insights, archive command, staff archiver, assistant, people data) correct without touching them. Paths that want children call children() (the relation bypasses the scope) or withoutGlobalScope(ParentOnly::class).
  • Route model binding must resolve a child: override resolveRouteBinding() to drop the scope, otherwise /app/board/{child} 404s. Same for the MCP tools' whereKey() lookups.
  • WorkItemObserver::saved(): return early for a child before calendar sync and stint recording.

Controller

  • store(): optional parent_id. When present: load the parent without the scope, check tenant, authorizeAccess on the parent, refuse a grandchild, copy employee_id, type, project_id, timesheet_category_id, force status = todo, sort_order = next under that parent. Return the child payload plus the parent's fresh card html.
  • show(): payload gains parent (id, title) for a child, and children (id, title, status, due_label, first participant) for a parent.
  • move(): for a child, status limited to todo/done, no ids reorder, response includes the parent's card html. For a parent, the done gate.
  • update() / destroy(): authorise against the parent when the item is a child. parent_id is not editable (prohibited).
  • archive() / restore(): cascade to children in the same transaction. Children cannot be archived on their own (422).
  • Remove toggleSubtask() and its route from the checklist build.

MCP

  • CreateCardTool: optional parent_id, same rules as store().
  • MoveCardTool: done gate on a parent, todo/done only on a child.
  • ArchiveCardTool / RestoreCardTool: cascade, refuse a child.
  • The read tools that list cards keep listing parents only (the scope does that), and add children to a single card's detail.

Front end

  • work-card.blade.php: wc--stack class and wc-sub counter from childSummary(). Needs children loaded, add it to cardHtml()'s loadMissing and the board query's eager load.
  • New partial partials/work-overview.blade.php rendered inside the scrim, driven by drawer.parent / drawer.children. Used by both boards.
  • work-board.js: drawer.parent, drawer.children, openChild(id), backToParent(), addChild(title), tickChild(id). The 422 from the done gate already surfaces verbatim in setStatus() and persistMove().
  • team-board.js: same state, no write methods.
  • CSS: .wc--stack, .wd-overview and rows, child drawer's two-state toggle. Remove .wd-sub-row from the checklist build.

8. Not in scope

  • Grandchildren.
  • Children in their own columns, or dragging a child between parents.
  • Children as their own timesheet rows, or on the calendar.
  • Converting an existing card into a child, or a child back into a parent.
  • Reordering children by drag. They keep creation order. Add when someone asks.
