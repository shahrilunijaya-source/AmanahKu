# CR-35 – Track effort: count submitted days, not only whole submitted weeks

| Field | Value |
|---|---|
| Module | API / Track integration |
| Priority | High |
| Tracker status | Open |
| Owner | Shazwan |
| Target | — |
| Run status | Not scheduled. Needs a session slot; it is not one of the 34 CRs split from the original tracker |

## Requirement
`GET /api/v1/timesheet-effort` must count a project entry once **its own day** is submitted or approved, instead of waiting for the whole week to reach `submitted`. A week that is part-submitted returns the effort of the submitted days and nothing else.

Legacy weeks that have no per-day rows keep being judged by their week status, unchanged.

## Why
Timesheets are submitted per day (CR-03: `WeekWriter::$submitDay` flips one `timesheet_days` row). The week-level `timesheets.status` only becomes `submitted` once every unlocked working day is submitted ([`Timesheet::refreshStatusFromDays()`](../../app/Models/Timesheet.php)). The endpoint filters on that week status ([`ApiController::timesheetEffort()`](../../app/Http/Controllers/Api/V1/ApiController.php), `COUNTED_TIMESHEET_STATUSES`).

So a staffer who submits Monday's day on Monday contributes nothing to Track until Friday's day is in. Track's nightly pull (`amanahku:sync-effort`, 02:00, four-week window) is already daily; it is asking a question AmanahKu only answers once a week. Money out in Track's ledger lags the work by up to five days, and the management meeting reads a week that looks emptier than it is.

Measured on the dev copy of the production dump, week 2026-09-14: one day submitted, one project entry against it, week status `draft`, endpoint returns `projects: []`.

## Scope
1. **Gate per entry date.** An entry on date D in timesheet T counts when T's `timesheet_days` row for D has status `submitted` or `approved`.
2. **Legacy fallback, per timesheet, not per date.** If T has **no** `timesheet_days` rows at all, fall back to T's week status exactly as today. If T has any day rows, day rows alone decide and a missing row means not submitted. Per-timesheet, because a per-date fallback would let a dateless day inherit a `submitted` week status, which is the leak this CR exists to close.
3. **Legacy is not a corner case.** All 133 `submitted`/`approved` timesheets in the current dump have zero day rows; the only timesheet that has day rows is `draft`. Without rule 2 this CR zeroes every historical figure in Track's ledger on the next nightly run.
4. **Payload shape unchanged.** Still one aggregate row per position band per week: `position_id, position_title, headcount, person_days, days_present, alloc_pct`. No employee name, id or salary crosses the wire, by construction.
5. **Docs in scope.** The endpoint docblock, `docs/API.md` ("A week is counted once it is `submitted` or `approved`") and the `ApiReference` blurb all state the week rule in prose and must state the day rule instead.
6. **No Track change.** Its cron already runs nightly over a four-week window, `AmanahkuEffortSync::composeRows()` maps whatever comes back, and `WeekNoteLedger` costs from `person_days`. Nothing on that side needs touching.
7. **Non-goal:** making the endpoint day-granular. It stays one aggregate per week; per-day effort in the payload is not asked for and is not built.

## Knock-ons to expect, not bugs
- Mid-week, `person_days`, `days_present` and `headcount` all read lower: only the people who have submitted appear, for only the days they submitted.
- `alloc_pct` can read **low** mid-week, and that is new. `days_present` counts distinct dates across the whole band, not each person's own days, so two full-time people covering different halves of the week report as 50% dedicated. Unreachable while a week counted all-or-nothing. `person_days` stays exact and is what Track costs from; `days_present` stays band-wide because making it per-person is a bigger change for no ledger benefit.
- A day returned for correction stops counting, so a project's money out can go **down** between two nightly runs. That is correct and someone will file it as a bug.
- Existing `TimesheetEffortApiTest` cases create no day rows, so they all land in the legacy branch and stay green. They are not evidence this CR works; the partial-week cases need new tests.

## Acceptance
1. Legacy week, no `timesheet_days` rows, week status `submitted` — every project entry counts, identical figures to today.
2. Day rows for Mon, Tue, Wed only, all `submitted`, week status `draft` — only Mon–Wed entries count. Thu and Fri entries, and any day row that is `draft`, `returned` or `rejected`, contribute nothing.
3. Day rows for every working day, all `submitted`, week status `submitted` — identical figures to today.
4. A `submitted` day returned for correction, then the endpoint called again — that day's effort is gone and the project's total drops.
4b. Two people in one band submitting disjoint halves of the week — `person_days` is exact, `alloc_pct` reads 50%. Pinned by a test so the reading is a known property, not a surprise.
5. A week with some day rows and a `submitted` week status never lets a day without a row count.
6. A `rejected` week contributes nothing even if a day row under it says `submitted`. Nothing writes that combination today (`refreshStatusFromDays()` overwrites a week's status once day rows exist) but a dead week must never leak effort, so the week-level veto stays ahead of the day check.
7. Tenant isolation, scope and role checks unchanged.
